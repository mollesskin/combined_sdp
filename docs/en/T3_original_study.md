# T3 — Original study

| Element | Description of this study |
|---|---|
| **Research question or hypothesis** | **Research question:** How effective are combinations of security design patterns, compared with their individual components, at preventing vulnerabilities in Ethereum smart contracts? The tested comparison asks whether V3 (A+B) improves the declared security outcome over **both** V1 (A only) and V2 (B only), while preserving legitimate behavior. |
| **Methodology and design** | A controlled, within-contract comparative experiment on existing vulnerable Solidity benchmarks. For a qualifying source file, the arms are V0 (unchanged original), V1 (pattern A), V2 (pattern B), and V3 (A+B). The same contract-specific normal and adverse scenarios are applied to each arm with a pinned compiler and local execution fixture. Source files and scenarios were selected purposefully, not randomly. Thirteen historical files had only a single repair and one auction file compared alternative refund workflows; those 14 do not enter the A+B denominator. |
| **Population, sample or dataset, and size** | The local SmartBugs Curated dataset contains **143 original Solidity source files** across ten vulnerability families. The frozen historical study selected **40** original files in five families; **37** obtained completed behavioral comparisons (23 four-arm, 13 single-repair, one alternative-workflow), and three remained unresolved. A later `simple_dao.sol` extension adds one completed four-arm file. Thus the current work has **41 considered / 38 completed** original files, including **24 full V0–V3 comparisons**. A file is counted once, regardless of the number of generated variants, test scenarios, or repetitions. |
| **Instrument: protocol and metric definitions** | The instrument is a set of source-specific behavioral protocols and executable test oracles, not a questionnaire. Each oracle checks the intended ordinary workflow and adverse conditions. Primary outcomes include safe rejection of unsafe arithmetic, authorized versus forbidden access/state transitions, excess ether payout (`max(0, payout − authorized amount)`) and accounting consistency, token-call failure handling and delivery shortfall, and requested/accepted/completed/rejected work for denial of service. **Gas used and transaction count are secondary resource measures** and are directly compared only for matched work and outcomes. Compilation and ABI checks qualify an arm; neither alone proves protection. Static analyzer scores from earlier work remain a separate instrument. |
| **Experimental or technical procedure** | Record the original source path, annotation, SHA-256, compiler version, permitted behavior, treatment edits, and fixed scenarios. Compile the unchanged V0 and materialized variants with their pinned Solidity compiler versions. Deploy each variant in a fresh local fixture; run the same permitted and adverse scenarios, record transaction status, state and balance changes, and applicable resource values. The 37 completed historical cases have **two saved primary clean runs** each; the new SimpleDAO case also has **two independent local runs**. Keep failures, `N/A`, and unresolved requirements explicit rather than treating them as successful protection. |
| **Analysis method applied** | Compare V3 with V1 **and** V2 separately on the primary behavioral requirements and preservation of legitimate functionality. Classify each completed four-arm source as better than both, equal to the best individual arm, worse than the best, trade-off, or inconclusive. Report counts by original file and vulnerability family; keep exploratory pilots and single-repair/alternative cases labelled separately. Use descriptive counts and direct scenario measurements only; no p-values, random-sample inference, or population-wide effectiveness estimate is claimed. |
| **Main reported result** | In the **frozen historical** set of 23 full comparisons, V3 was better than both single patterns in **0/23**, equal to the best in **21/23**, and worse in **2/23**. The two worse cases were denial-of-service capacity variants: at 5,950 requested records, incremental cleanup A completed all 5,950, while B and V3 accepted/completed 1,750 and rejected 4,200. The later SimpleDAO extension tied the best single arm, yielding a descriptive combined count of **0/24 better, 22/24 equal, 2/24 worse**. This added case does not alter the frozen historical result. |

**Interpretation.** The observed combinations did not improve on both component patterns in the tested scenarios. This is a bounded result: several historical arithmetic A/B pairs enforce the same no-wrap condition, six historical full comparisons were exploratory pilots, and related benchmark sources are not independent random samples. The stricter follow-up pair screen marks 14 historical full pairings N/A for the current independent-pair design and leaves nine historical pair audits pending. It would therefore be incorrect to present the 24 four-arm runs as 24 qualified independent-pattern experiments.
