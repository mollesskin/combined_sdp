## Conditions and exact target scope

V1 A: checked-arithmetic operation through a documented compiler-compatible helper, arithmetic first then validity postcondition. New helper is AI-assisted code, not a claimed original SafeMath library. add computes c=a+b and requires c>=a; sub computes c=a-b and requires c<=a; mul computes c=a*b and requires a==0||c/a==b. require is deliberately consistent for new helpers; no assert gas-burn confound. BECToken uses its ALREADY DECLARED SafeMath.mul for the newly protected raw multiplication; existing SafeMath/sub/add/pause rules remain unchanged.

V2 B: exact pre-operation operand Guard Checks, not arbitrary business caps: addition b<=MAX-a; subtraction b<=a; multiplication a==0||b<=MAX/a (division avoided for zero). Actual operands at that execution point, not stale/pre-transfer state. All existing validation is kept. V3 combines the same B checks with the same A operations. A/B overlap the same no-wrap property by design; expected ties are permitted. Code/placement differ (post-result helper vs in-place operand guard), no claim of independent protection classes. No weakened arm.

- BECToken: ONLY batchTransfer count*value before existing checks; existing SafeMath library already protects balance debit/credit. Retain count limit1..20 and value>0. ## Common oracle, exactness and cases

MAX=2**256-1, MOD=2**256, ETHER=10**18. Node/ethers arithmetic and references use BigInt exclusively for uint256/storage/balances/wei/gas and large inputs. JSON/CSV serialize them as decimal strings. No Number conversion or IEEE-754 exponent reference. Addresses deterministic local signers, not random wallets. Scenario setup and sequence fixed across arms; hardhat_reset before EVERY scenario/variant and a fresh process per full repetition. No hardhat_setStorageAt, balance fabrication, code replacement or invented baseline funding path. Actor ETH allocated by normal local Hardhat genesis only; no real funds.

Valid input: every reached target mathematical intermediate lies in[0,MAX] and existing business constraints are met. Correct behavior is receipt success plus exact reference state/accounting. Unsafe reached arithmetic requires outer rejection and full rollback of contract state, contract ETH, observed storage and account token/entitlement records. A completed wrapped result is a violation, not an infrastructure failure. Non-reached arithmetic on an early-return branch is not an unsafe operation. A contract blocking all input fails functionality.
