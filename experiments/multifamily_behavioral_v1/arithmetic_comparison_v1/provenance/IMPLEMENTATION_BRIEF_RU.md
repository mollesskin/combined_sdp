# Следующий этап: три категории, исходники из проверенного архива

## Рамки

Утверждённый RQ не менять. Не возвращать основной объём к reentrancy-only. Сохранить прежние статические и поведенческие пилоты и vendor/pinned. Работать в отдельной ветке/копии. Предыдущие результаты baseline уже известны: это развитие экспериментального дизайна, не полностью независимая preregistration до всех данных.

Проверенный пул — 33 пути исходников; карта — `contract_review_33.json`. Число будущих пригодных A/B/A+B наборов пока не измерено. Не превращать цель «больше контрактов» в обязательство объявить все 33 полноценными комбинационными случаями.

## Две таблицы вместо одного ложного размера выборки

1. Реестр всех 33 baseline-кейсов: исходная категория, непосредственный механизм, hash, группа сходства, источник теста, результат авторского baseline-запуска.
2. Реестр полноценных сравнений: case/pair ID, A/B-definition, V0/V1/V2/V3, compiler, functionality status, behavioral outcomes и missing reasons.

Случай с единственным обоснованным исправлением может остаться в первой/отдельной single-fix таблице, но не становится evidence сочетания по умолчанию. Перекрытие эффектов A/B допустимо; идентичный код под разными названиями — нет.

## 1. Arithmetic: начать реализацию на всех 13 зарегистрированных файлах

A: compiler-compatible checked arithmetic (SafeMath или явно описанная адаптация).
B: точные проверки допустимого диапазона операндов на тех же целевых местах.
A+B: оба механизма без удаления частей A/B.

Это сравнение избыточной защиты одного no-wrap свойства. Предположение о преимуществе комбинации не закладывать. Gas/размер кода — вторичные затраты, не доказательство защиты.

Для каждого файла заранее зафиксировать список целевых операций; он есть в SOURCE_EVIDENCE/registry. Не считать появление SafeMath в файле гарантией его применения: в BECToken raw multiplication находится до проверок, хотя библиотека уже объявлена.

Правильные oracle-правила для положительного теста и небезопасного входа должны быть одинаковы для всех условий. Сохранять precise BigInt: tx status, входы, state before/after, математический эталон, признаки wrap, изменение балансов и raw error. Unsafe-input revert при полном откате — корректная защита, но блокировка допустимого ввода — functional regression.

Важные условия:
- не переходить на Solidity 0.8 только в защищённых версиях;
- обход ранней ветки init/run должен оставаться тем же;
- для token учитывать self-transfer и промежуточное состояние;
- mapping example начинается с нулевых записей и не имеет пути пополнения: не выдумывать обычное положительное списание;
- для overflow_single_tx локальные операции без state effect отделены от трёх проверенных state-changing операций;
- gas успешных операций отделить от gas неуспешных; не смешивать assert и require без учёта различий.

## 2. Access control: работать по подтипам, не по одной папке

Первая группа для разработки: `incorrect_constructor_name1`, `incorrect_constructor_name2`, `incorrect_constructor_name3`, `wallet_03_wrong_constructor`.

Перед реализацией объяснить, почему рассматривается самостоятельный initializer и кто законная authority. A — authority guard, B — once guard, V3 — оба. Отдельно указать constructor-based исправление как инженерный ориентир; не уничтожать исходный baseline. Три Missing-файла объединить в группу сходства.

Проверять запрещённую первую инициализацию, допустимую первую и повторную, последующие законные действия и изменения state. Не требовать superiority только из-за отклонения идемпотентного повторного вызова. Нормальные deposit/withdraw/допустимое администрирование не должны исчезнуть.

Следующие случаи анализировать по карте:
- `arbitrary_location_write_simple`: bounds guard + checked length arithmetic с перекрывающимся эффектом;
- `wallet_04_confused_sign`: entitlement guard + checked debit, но существующий baseline отвергает допустимое частичное снятие — явная функциональная оговорка;
- `proxy`: caller authorization + trusted target policy только после фиксации допустимого domain;
- `unprotected0`: owner authorization + two-step ownership только как явно изменённый workflow.

Не делать фиктивную пару:
- Parity already contains one-time guard;
- `wallet_02_refund_nosub` требует корректного accounting, а не запрета всем, кроме owner;
- `mycontract`/`phishable` прежде всего требуют исправления tx.origin authentication. Подписи/allowlist — не вытекающие автоматически из исходника требования.

## 3. DoS: не останавливаться из-за статических детекторов

Все четыре файла остаются в наблюдаемом пуле.

`dos_simple`: прежде изменить измерительную копию. Null receipt после одного блока — pending/noninclusion; зафиксировать отсутствие/наличие включения отдельно от execution status. Нужен фиксированный test gas/block budget и проверка прогресса/конечного состояния, cleanup automine в finally. Старый авторский результат не удалять.

`dos_address`, `dos_number`, `dos_simple`: разработать требования к ограниченной очистке и допустимой ёмкости/нагрузке. A — ограниченная пошаговая работа. B — ограничение роста/входного объёма при обоснованной политике. A+B — сочетание. Считать отказ в законной новой работе или уменьшение доступной ёмкости trade-off, не автоматическим успехом защиты. Не ставить cap ниже порога >1500 так, чтобы очищение стало недостижимым. Согласовать новое число вызовов/состояния очистки до тестов.

`auction`: отдельная проблема отказа получателя, не цикл. Можно сравнить pull payment и push-with-fallback-credit как альтернативы. Их общие deferred-refund элементы не превращать автоматически в независимую комбинацию. Исследовать выплату долга и новую ставку на уровне workflow, а не требовать сохранения мгновенной выплаты. При отсутствии недублирующей пары честно оставить этот кейс в single-fix/alternative comparison.

## Измерения

Access: запрещённое изменение полномочий/state, неразрешённый отток в wei, сохранённые допустимые действия.
Arithmetic: exact discrepancy относительно математического эталона, rollback, supply/accounting, допустимые операции.
DoS: завершённая работа/прогресс при фиксированных бюджетах, отклонённая нагрузка, число вызовов до завершения, учтённые неполученные выплаты.

Не складывать wei, tokens, counts, gas и scores в универсальную шкалу. Старую PES не менять и не считать по поведенческим данным. Дополнительную пользу оценивать отдельно V3−V1 и V3−V2 по сопоставимым свойствам с функциональными ограничениями. Повторы не являются новыми контрактами. Все значения — только из действительных выполнений.

## Порядок доставки

Сначала реализация общей точной измерительной части и arithmetic-набора; параллельно явная спецификация initializer и DoS workflow. Затем четыре варианта для квалифицированных случаев и реальные локальные runs с raw evidence. Не перезапускать старые reentrancy-пилоты вместо новых категорий. Отдельный неготовый кейс не останавливает все остальные; сохранять его причину, а не заменять ради удобного результата.

Этот документ — план реализации. Никакой его пункт не означает, что новые варианты уже скомпилированы или показали конкретный результат.
