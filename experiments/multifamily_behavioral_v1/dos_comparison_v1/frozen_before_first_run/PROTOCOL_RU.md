# DoS behavioral comparison v1

RQ: “How effective are combinations of security design patterns compared with their individual components in preventing vulnerabilities in Ethereum smart contracts?” AI-assisted реализация; не текст assignment. Arithmetic и access control не запускаются/не меняются, hashes всех их файлов проверяются read-only. PES не вычисляется/не изменяется. Статические детекторы не критерий включения. Протокол, код и параметры фиксируются до новых comparative executions, но авторские baseline-результаты известны: это не preregistration до любых данных.

## Четыре модели и условия

Фактические исходники/тесты и CONTRACT_MAP прочитаны. Исходники и тесты проверены по SHA-256 обзора, сохранённого в inputs. V0 побайтово исходный. Никаких чужих исходных тестов повторно не выдаём за защитные данные.

**Auction:** higher bid должен сменить leader, несмотря на отказ бывшего bidder получать ETH. Права прежнего bidder на возврат должны сохраняться: immediate payout или зарегистрированный claim, который может получить только этот bidder (в том числе указав принимающего получателя). Latest bid остаётся в auction. V0 — прежний обязательный push. PULL — credit при outbid и отдельный withdrawRefund(recipient). FALLBACK — попытка исходного send, при отказе сохраняется тот же credit; withdrawRefund общий. Это альтернативные workflow с общим deferred-credit механизмом, не A/B и не фиктивный A+B; batching нет. API additions: refunds(address), withdrawRefund(address). Mapping после оригинальных fields сохраняет slots0/1. CEI: claim zero до transfer, revert восстанавливает claim. Нулевая claim не даёт средств. Получателя выбирает именно владелец claim. Baseline failure принять bid не считается потерей refund debt: outbid не произошёл и деньги остаются backing старой live bid.

**dos_address:** публичный addCreditors принимает пакет350 адресов caller. emptyCreditors после length>1500 намеренно удаляет записи и ставит win; никаких денежных требований/балансов этих «creditors» в исходнике нет. Общая задача — принять запрошенные пакеты и завершить явное удаление принятого массива. A/V1 — шаг удаления максимум350 элементов с сохраняемым clearing flag и продолжением ниже1500; add временно запрещён до конца cleanup. B/V2 — cap1750, require до принятия всего пакета, исходный atomic cleanup сохранён. V3 оба механизма. Win не сбрасывается при refill (как в baseline).

**dos_number:** insertNnumbers(value,numbers) сохраняет числа; clearDOS после numElements>1500 должен физически удалить массив и установить logical/real lengths0. A/V1 — physical cleanup шагом350, сохраняемый clearing, уменьшаемый numElements; insert и отдельный clear временно запрещены в процессе. B/V2 — accepted active volume <=1750 (без partial acceptance), clearDOS прежний. V3 оба. У исходного clear() другая семантика: только logical length0 при сохранённом allocated array, и reuse должен работать. Этот путь не заменяется physical deletion. A не чинит произвольный огромный insert loop: separate oversize scenario сохраняет это ограничение.

**dos_simple:** исходный ifillArray уже ограничивает рост: при length<1500 добавляет350, максимальная достижимая длина1750. Поэтому отдельный cap как новая B не обоснован. V0/F1 single-fix: bounded cleanup350, clearing flag, продолжение до0, затем следующий вызов снова fill350. false return остаётся признаком cleanup branch, не обязательно завершения. Транзакций очистки становится больше. Новое clearing() во всех A/F1 — API для наблюдения workflow, не доказательство эквивалентности.

Лимит1750 = минимальное целое число исходных пакетов350, позволяющее перейти >1500 (5 пакетов). Это явная экспериментальная политика ёмкости, НЕ исходное business requirement: она отклоняет часть запрошенной ранее допустимой нагрузки. Не считать B/V3 полностью решающим общий requested workload при reject. Сравнения используют общий знаменатель requested; отдельно показывают completion принятой части. Порог очистки остаётся достижимым. Данные не теряются при admission: rejected batch атомарно не меняет массив. Только явно запрошенная cleanup операция удаляет принятые записи. Работа публичная; исключительных owner-прав не вводится.

## Фиксированные сценарии и бюджеты

Local Hardhat only, no forks/public networks/real funds. Compiler matrix исходного проекта (0.4.24/0.4.25/0.5.0), optimizer исходный; Shanghai/initialDate исходные, blockGasLimit явно зафиксирован30,000,000. Reporter spec. Dependencies скопированы manifests без изменений; node_modules ссылка на baseline. Actual compiler/settings/ABI сохраняются. GasLimit каждой измеряемой транзакции **12,000,000**, включая insertion/cleanup/auction; сравнение gas только при сопоставимом объёме/состоянии/status.

Для address/number два основных сценария: **5×350=1750** и **17×350=5950** ненулевых записей (исходные нагрузки авторского normal/attack тестов). Number value=1; address caller=user0. Все requests посылаются, в том числе после достижения cap: каждый reject остаётся в requested/rejected denominator. Никакого ретюнинга нагрузки после результатов.

На cleanup: максимум20 tx, суммарный разрешённый лимит240,000,000 gas; на load — ровно5 либо17 tx. Общий максимальный workflow budget: (load tx+20)×12m, т.е.300m/444m gas и25/37 tx. После первого mined revert без прогресса cleanup прекращается как bounded-operation failure; отсутствие завершения при данном бюджете не доказывает вечную недоступность. Для A продолжать только при строго уменьшающейся длине, до0; successful no-progress завершается как stalled. Pending не приравнивается execution revert; при pending — missing completion, отдельно status. Полный успех задачи требует requested=accepted=completed и правильный final state. Partial capacity completion — компромисс, не общий success.

После successful cleanup — один отдельный refill350 (postcondition/functionality check, вне основного completion budget), проверить содержимое и разрешённость нового цикла. После failed cleanup refill не подменяет незавершённую задачу, N/A. Дополнительно number: 5 load batches, clear() до logical0/real1750, insert350 value9, проверить prefix9 и сохранённый unused suffix1; budget7tx84m. Oversize insert numbers5000 value1 отдельным fresh deploy,1tx12m: неуспех не считать защитой, denied volume5000 остаётся в denominator.

Для dos_simple normal cycle: 5 fill calls=1750 записей, затем до20 cleanup calls с теми же12m/240m. Общий budget25tx300m; refill350 отдельно. Lower budget gas retuning нет. У этого контракта нагрузка5950 недостижима в одном fill cycle: не искусственно inject storage, не менять destination функции. Естественный порог/ёмкость отражены в реестре.

Для auction: fresh deploy; первые ставки10 wei от user1 (normal EOA) или owner-controlled refusing BidderFixture; higher bid20 wei user2; equal bid20 от user0 должен безопасно отказаться. PULL: отдельный claim возвращает10. FALLBACK: immediate payout10 нормальному EOA или claim10 refusing fixture. Refusing fixture пробует claim на свой reverting fallback (долг должен сохраниться), затем claim на EOA своего controller (10), затем повтор claim (0 дополнительных средств). V0, где higher bid отказал, не получает выдуманный refund claim: recovery N/A, bid-progress failure и старый live bid10 раскрыты. Если immediate payout уже был — deferred claim N/A, не ноль «потерянного долга». Максимум8 измеряемых calls/96m gas на сценарий; сумма шагов, сохранение debt и eventual payout важнее одной successful bid. Zero-payout repeat не считается ещё одной выплатой. Tx gas корректируется при сравнении EOA balances.

## Статусы и дополнительные проверки

Отдельный dos_simple status scenario для V0/F1: automine=false, interval0, отправить4 fill tx с gasLimit12m при block30m; mine один блок, сохранить receipt/null и transaction existence; затем ещё до3 блоков, записать конечный receipt/pending отдельно. Pending после одного блока — только noninclusion, не DoS execution failure. Все эти четыре requests=1400, данные должны сохраниться. Очистку не вызывать в этом сценарии. Cleanup automine=true/interval0/reset в finally. Дополнительный диагностический gasLimit30,000,001 >blockBudget запрос намеренно должен быть rejected_before_inclusion: он проверяет классификатор и исключён из эффективности workload.

Execution status: pending (hash/tx известны, receipt нет), success (status1), reverted (mined status0), rejected_before_inclusion (идентифицированный admission RPC rejection без hash/receipt), infrastructure_error (остальное; result missing/null). Ошибки не нули и не защиты. Receipt gas каждого шага сохраняется; для pending/pre-inclusion gasUsed=null. Mined revert проверяет state rollback, не даёт выполненной работы.

Запись прогресса: requested/accepted/rejected (из-за capacity либо execution failure) volumes; cleanup completed work/accepted и completed/requested с явными denominators; before/after lengths, flags и samples, full record content before cleanup и final cleared slots; число tx и successful/no-progress шагов; gas шагов и total по фазам. Gas отдельно от work/wei/violations; PES и общая шкала отсутствуют. Auction: live bid backing, refund obligations, paid amounts, final balance, claims rollback. N/A/null остаётся null. Ошибки compile/setup — registry/missing, не успех.

Два итоговых process runs с clean compile/reset и новыми output paths. Источники, groups, варианты, scenarios и повторы считать отдельно. Четыре singleton группы по существующему ограниченному обзору не доказывают независимости. V3 сравнить отдельно с V1/V2: full requested completion, accepted-part completion, capacity reject, functionality, steps и gas. Подготовительные прогоны/исправления инструментов сохранять отдельно; условия не менять ради преимущества комбинации. После этой партии остановиться.
